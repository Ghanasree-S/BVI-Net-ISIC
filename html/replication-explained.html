Rebuilding BVI‑Net

The paper claims a skin-lesion segmentation network with 26,000 parameters and released no code. We rebuilt it from the written description in PyTorch, drove the parameter count from 777,584 down to 27,312, and trained it on ISIC2018 to see how much of the claim survives contact with a real implementation.

Premise

A claim with no code behind it is a hypothesis. This is the experiment.

What we were actually testing

BVI-Net's headline is not its accuracy — plenty of models beat 90.43 Dice on ISIC2018. Its headline is accuracy at that accuracy for 26,000 parameters. Everything interesting about the paper lives in that ratio.

And that ratio is precisely what an unreleased implementation makes impossible to check. The architecture is described in prose; the exact channel widths of the five encoder stages, the number of graph nodes in the skip connections, and the fusion arithmetic are not all pinned down. Two people reading the same paragraphs can build models that differ by an order of magnitude in size. So we set three objectives, in strict priority order:

  1. Reimplement BVI-Net from the published description alone, in PyTorch, with no reference code to peek at.
  2. Verify the 0.026M parameter budget — is it reachable by an honest reading of the paper, or does it require something the text doesn't say?
  3. Reproduce the reported ISIC2018 accuracy, and where we fall short, say by how much and why.

We deliberately scoped out everything not needed for that: no LiTS17 liver task, no BraTS19 brain task, no reimplementation of the competing models in the comparison tables, no ablation study. One task, one model, done properly.

Result in one sentence

The parameter claim holds up — but only once you read one specific sentence about weight sharing correctly. The accuracy claim we got within four points of, on a test set that is not the paper's.

01 Data

The paper's test set does not exist publicly. Everything downstream has to account for that.

Getting the data honest first

ISIC2018 Task 1 (Lesion Boundary Segmentation) publishes 2,594 training images with expert-drawn masks, plus a 100-image official validation set whose masks are also public. It also has a 1,000-image official test set — and those masks have never been publicly released. Scores on it come back only through the challenge's own submission server.

That is a hard wall, and it is worth being blunt about what it means: nobody outside the challenge can reproduce the paper's exact test numbers. Not us, not anyone. So we did the next most honest thing:

  • Validation = the official 100-image set. Same images, same masks, same count as the paper. Model selection happens on exactly the data the paper selected on.
  • Test = 259 images carved off the training pool before training and never touched again. Ours, not the paper's — but genuinely held out.
  • Train = the remaining 2,335 images.

Preprocessing is minimal and matches the paper: everything resized to 256×256, masks nearest-neighbour so they stay binary. Augmentation — flips, 90° rotations, shift/scale/rotate, brightness/contrast and HSV jitter — is applied to the training split only. Validation and test see raw images, which is the only way the numbers mean anything.

Naming bug worth fixing before submission

The output folder is called isic2018a and evaluate.py prints “Test set results (ISIC2018-a)”. That name is a leftover from an early plan to use the paper's quarter-sized ISIC2018-a ablation subset. The final run used --fraction 1.0, i.e. the full 2,594-image pool — which is the right choice, since it matches the paper's main results table rather than its ablation table. Only the label is wrong, not the data.

02 Build

Three modules, roughly 250 lines of model code, no reference implementation.

Building the three modules from prose

Each of the paper's three contributions became one file. Here is what each one actually does, and where we had to make a judgement call the paper left open.

Local Pathway — models/gabor_conv.py

Four 5×5 Gabor kernels at 0°, 45°, 90° and 135° are generated analytically, applied depthwise to every input channel, and mixed down to the output width by a 1×1 convolution. The orientation bias multipliers (×1.18 for the V1/V2 stages, ×1.26 / ×0.74 for the V4 stages) are registered as a fixed buffer, not a parameter — so they shape the response without costing anything.

models/gabor_conv.pythe shared kernel, and how it is applied
# shared depthwise kernel: one per orientation, reused across every input
# channel -- this is the actual weight-sharing the paper describes.
base = torch.stack([
    gabor_kernel(kernel_size, math.radians(o)) for o in orientations
])                                              # (4, k, k)
self.depthwise_weight = nn.Parameter(base.unsqueeze(1))   # (4, 1, 5, 5) = 100 params

# pointwise projection mixes the 4 x in_channels filtered maps to out_channels
self.pointwise = nn.Conv2d(in_channels * 4, out_channels, kernel_size=1)

def forward(self, x):
    b, c, h, w = x.shape
    weight = self.depthwise_weight.repeat(c, 1, 1, 1)   # view of the SAME 100 numbers
    weight = weight * self.orientation_bias.repeat(c).view(-1, 1, 1, 1)
    x_rep  = x.repeat_interleave(4, dim=1)
    filtered = F.conv2d(x_rep, weight, groups=c * 4)
    return self.pointwise(filtered)

Global Pathway — models/fa_vssm.py

The four scan orders are computed once per feature-map size and cached. Line and column are trivial index permutations; the Z-curve is built by bit-interleaving the x and y coordinates; the Hilbert curve uses the standard d2xy recursion. Each order permutes the flattened pixels, the SSM runs along the sequence, the result is scattered back, and the four are averaged.

Alongside them, the fast-attention channel is exactly what the paper describes and nothing more — an average-pool and a max-pool across channels, concatenated, one 7×7 convolution, a sigmoid.

models/fa_vssm.pyfour scans, one average
MODES = ("line", "column", "zcurve", "hilbert")

def forward(self, x):                          # x: (B, C, H, W)
    flat = x.flatten(2).transpose(1, 2)        # (B, HW, C)
    outs = []
    for mode in self.MODES:
        order     = self._get_order(h, w, mode, x.device)
        scanned   = flat[:, order, :]          # reorder pixels
        processed = self.ssm(scanned)          # Mamba selective scan
        unscanned = torch.zeros_like(processed)
        unscanned[:, order, :] = processed     # put them back
        outs.append(unscanned)
    merged = torch.stack(outs, dim=0).mean(0)  # average the 4 directions
    return merged.transpose(1, 2).view(b, c, h, w)

GCN Attention — models/gcn_attention.py

A 1×1 convolution plus softmax produces the pixel-to-node assignment; a batched matrix multiply pools pixels into N nodes; a learned adjacency matrix (initialised as identity plus small noise, so it starts as a no-op and learns its structure) mixes the nodes; the transposed assignment paints the result back onto pixels, added as a residual.

Judgement call: the paper does not state N. We made it a command-line flag and swept it alongside the channel widths.

Assembly — models/bvi_net.py

Five encoder stages, roles ["v1v2", "v1v2", "v4", "v4", "v4"], each running both pathways and fusing them. The fusion line is the whole bio-visual interaction in two statements:

models/bvi_net.pyGlobal guides Local
local_feat  = self.local(x)                        # fine edge features
global_feat = self.global_path(self.global_in(x))  # fast global context

gate  = torch.sigmoid(global_feat)                 # squash to a 0-1 highlighter
fused = local_feat * gate + local_feat             # residual-gated fusion

skip = fused                                       # sideways to the decoder
down = self.pool(fused)                            # downward to the next stage
Why + local_feat and not just the multiplication

A pure multiplicative gate is dangerous early in training: when the Global Pathway is still random, a sigmoid output near zero would zero out the Local Pathway's features entirely, and a zeroed feature has no gradient to learn from. Adding the local features back guarantees that detail always survives, and the gate can only amplify what is already there. The paper describes multiplicative guidance; the residual is our reading of how to make it trainable.

03 Shrinking

The first working model was thirty times over budget. That is the interesting part.

It worked immediately, and it was 30× too big

The first complete build produced correct-shaped masks and trained to a respectable 0.8536 validation Dice. It also had 777,584 parameters — thirty times the paper's claim. Every individual module matched the description; the total did not match the number.

That is the standard failure mode of replicating an architecture paper: the prose constrains the structure, not the widths. Our first guess at channel counts was the conventional doubling ladder 8 → 16 → 32 → 64 → 128, which is what almost every U-Net variant uses. The paper never says that is wrong; it just never says what is right.

So we wrote width_search.py — a short sweep that trains three width configurations for a reduced 20-epoch budget and reports parameters against best validation Dice. One constraint fell out immediately: every channel count must be divisible by 4, one per Gabor orientation, which is why the configurations look the way they do.

Two things in that table are worth pausing on.

The biggest model was the worst. 777K parameters scored below 202K parameters, which scored above 37K. On 2,335 training images, the largest configuration is simply overfitting — exactly the argument the paper makes for going small in the first place. We reproduced the paper's motivation by accident before we reproduced its result.

We did not pick the winner. narrow-1 had the best sweep score, but at 202K it is eight times the paper's budget — and the budget is the claim we came to test. We took narrow-2, giving up 1.7 points of 20-epoch validation Dice to get within striking distance of 26,000. Over a full 50-epoch run with a learning-rate schedule, narrow-2 later recovered to 0.8711, most of the way back.

That left us at 37,144. Still 43% over. Closing the last gap needed a different kind of fix — not a smaller model, but a correctly-read one.

04 The fix

One sentence in the paper, misread, cost 9,832 parameters.

The sentence we had been reading wrong

Our first Gabor layer did this: generate the four Gabor kernels, tile them out across every input–output channel pair to fill a full dense convolution weight tensor, apply the orientation bias, and register the whole tiled tensor as the learnable parameter.

That is Gabor initialisation. Every weight starts from a Gabor shape — and then every weight is stored and learned independently. The layer has exactly as many parameters as an ordinary convolution. We had implemented the biology and thrown away the entire cost saving, while our own code comment cheerfully claimed “weights are shared to keep the layer ultra-lightweight”.

The paper does not say the kernels are Gabor-initialised. It says the weights are shared. Those are completely different claims, and only one of them makes 0.026M possible.

The arithmetic closes exactly:

Model before the fix37,144
− dense Gabor local pathway− 12,456
+ shared Gabor local pathway+ 2,624
Model after the fix27,312
Paper's claim26,000
The result that matters

Validation Dice went up, from 0.8622 to 0.8711, while parameters fell 26%. Sharing the oriented kernels across channels is not a compression compromise that costs accuracy — on this task it is the better model. That is a genuinely strong piece of evidence for the paper's design, and it is the single most useful thing our replication found.

With that, the parameter claim lands within 5%. Whatever residual 1,312 parameters separate us from 26,000 is well inside the range of the unstated details — a slightly different N, one fewer batch-norm, a different bottleneck width.

05 Training

Kaggle T4, real Mamba kernels, 50 epochs, no overfitting anywhere.

Training the final model

One thing we were determined not to fudge: the real Mamba selective-scan backend. models/fa_vssm.py contains a fallback — a depthwise-conv-plus-gate approximation used when mamba_ssm cannot be installed, which on Colab is often. A fallback would have meant reporting numbers for a model that isn't quite the paper's.

Getting the real one working took a fight. mamba-ssm compiles a CUDA extension against the exact PyTorch build present at install time, so pinning torch in requirements.txt silently downgraded Kaggle's preinstalled stack and broke the freshly-compiled extension. The fix was to stop pinning torch and torchvision entirely and let the platform's GPU-matched build stand. The final run reports causal-conv1d 1.6.2 and mamba-ssm 2.3.2 built successfully — genuine selective scan, not the approximation.

If you re-run this on a CPU

Without mamba_ssm, the same 4-8-8-16-16 configuration reports 19,280 parameters instead of 27,312, because the fallback branch is far smaller than a real Mamba block. That is not a bug and not a better result — it is a different model. Only the 27,312 figure is comparable to the paper.

Three deliberate departures, all forced and all documented:

  • Batch 8, not 64. The four-way scan holds four permuted copies of the feature map in memory at once. Batch 64 does not fit a T4 at 256×256.
  • Patience 15, not 5. With patience 5 training kept stopping in the twenties, right before a learning-rate drop would have paid off. Look at the curve below — the best score arrives at epoch 47, long after a patience-5 rule would have killed it.
  • A plateau scheduler the paper doesn't mention. Every one of our validation-Dice records after epoch 19 follows a learning-rate halving. Without it the model stalls around 0.85.

Reading the pattern, not the individual numbers

The shape of the gap says more than its size. Specificity is higher than the paper's, sensitivity is lower by 2.97, and accuracy is almost identical. That is a coherent, single-cause signature: our model is more conservative than the paper's. It is more reluctant to call a pixel “lesion”, so it almost never flags healthy skin (high specificity) but it clips the faint outer edges of lesions (lower sensitivity, and therefore lower Dice and mIoU).

This is the classic behaviour of a model that is slightly under-trained or slightly under-capacity at the boundary, and it is exactly what you would expect from three of our known deviations working together — a smaller batch, a scheduler that anneals the learning rate to 0.00003 by the end, and possibly a hair less capacity than the paper's own widths.

It is not the signature of a broken implementation. A wrong architecture produces incoherent metric patterns — high sensitivity with terrible specificity, or accuracy far off while Dice looks fine. Ours all move together in one direction, with one metric ahead.

On the boundary metric

ASSD came out at 6.88 pixels on 256×256 images — meaning the average point on our predicted outline sits about seven pixels from the true outline. The paper's ASSD for the skin task isn't in our comparison set, so this number stands alone rather than as a comparison. It is consistent with the conservative-boundary story: a slightly shrunken mask keeps a good Dice while pushing the surface distance up.

Which parts of the design actually spend the budget.

Where the 27,312 parameters actually live

Worth knowing, because it tells you where any further shrinking would have to come from — and because the answer is not where most people would guess.

Three observations fall out of this:

  • The Global Pathway is the most expensive component, at 40% of the whole model — and almost all of that is the Mamba block's internal projections, not anything BVI-Net added. The scanning, the averaging and the fast attention are nearly free; the SSM itself is the cost.
  • The Local Pathway — the paper's signature contribution — costs 9.6%. Of its 2,624 parameters, only 500 are the actual Gabor kernels; the rest are the 1×1 projections and batch-norm. The headline module is close to free, which is exactly what the paper promises.
  • The decoder is the quiet third of the model. Its plain 3×3 fusion convolutions consume 33% — more than the Local Pathway, Global-Pathway-minus-Mamba and GCN skips combined. If anyone wanted to shave the last 1,312 parameters to reach 26,000 exactly, this is where the fat is, and it is the least architecturally interesting part of the network.

What we did not test at all

  • 0.025 GFLOPs and 292 FPS. Never measured. Both are perfectly checkable with a profiler and a timing loop — this is the cheapest remaining gap to close.
  • LiTS17 (liver) and BraTS19 (brain). Deliberately out of scope. The paper's cross-organ generality claim is untested by us.
  • Ablations. We never removed the Gabor pathway, the FA-VSSM or the GCN skips one at a time, so we cannot say what each contributes. The one exception is accidental: swapping dense Gabor for shared Gabor raised Dice by 0.9 points, which is a partial ablation of the weight-sharing claim, and it came out in the paper's favour.
  • Baseline models. No U-Net, MALUNet or EGE-UNet was trained on our split, so our 86.31 has no in-house reference point.
The fairest summary

We verified the parameter claim — and in doing so identified the specific mechanism (true weight sharing, not Gabor initialisation) that the claim depends on. We did not verify the accuracy claim; we got within 4.12 Dice points on a different test set, which neither confirms nor refutes 90.43. And we did not test the efficiency claims at all.

Conclusion

What we would tell someone deciding whether to build on this paper.

Is BVI-Net reproducible?

Yes, with one caveat that we think is worth writing down.

The architecture reconstructs cleanly from the prose. All three components — the Gabor local pathway, the four-way scanning FA-VSSM, the graph-attention skips — are implementable from the description without guessing at anything structural, and they train stably first time. That is not true of every architecture paper.

The size claim is real, but it is load-bearing on one sentence. Read “the weights are shared” as “the weights are Gabor-initialised” — which is the more common design in the literature, and which our own first implementation did while its comment claimed otherwise — and you land at roughly twice the parameter count with no way to see why. A single sentence carrying the entire headline claim, with no code to check it against, is a fragile place for a result to live.

The accuracy claim we can neither confirm nor deny, and neither can anyone else outside the ISIC challenge, because the test masks are not public.

The design finding

The most useful thing we learned is not a number. It is that sharing one oriented kernel across every channel improved accuracy while cutting parameters. The lightweight design is not a trade-off being tolerated for deployment reasons — on a 2,335-image medical dataset, the constraint is the regularisation. That is the paper's real argument, and our run supports it.

What we would do next

  1. Measure GFLOPs and FPS. An afternoon's work, and it closes a third of the unverified claims.
  2. Run the ablations properly — Gabor off, FA-VSSM off, GCN skips off, one at a time.
  3. Repeat with 3–5 seeds so the 4-point gap gets an error bar and stops being a single anecdote.
  4. Extend to LiTS17 and BraTS19 to test the cross-organ claim.
  5. Ship a small web front-end — upload a dermoscopy image, see the mask. At 27K parameters the model runs in a browser, which is a genuinely good demonstration of why any of this matters.

Two ways to get the wrong answer

Pinning torch. requirements.txt deliberately leaves torch and torchvision unpinned. Pinning them downgrades the platform's GPU-matched build and silently breaks the CUDA extension mamba-ssm just compiled against it — the model then falls back to the approximation without telling you.

Mismatched --channels. evaluate.py rebuilds the model before loading the checkpoint, so the widths passed to it must match the ones used for training exactly, or the state dict will not load.
